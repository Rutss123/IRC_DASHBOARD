1. MIKROTIK RADIO STATISTICS

The dashboard was extended to monitor the mANTBox ax and NetMetal ax through
the backend. The collector polls RouterOS over HTTPS and the backend exposes
snapshots through GET /api/radio-link. The dashboard polls every five seconds.

The radio panel displays API status, signal strength, TX/RX link rates and
throughput, CPU and memory information, and recent-sample charts. Noise floor
and SNR appear when usable values are available. Browser-session graphs keep
up to 600 samples. During bench testing both radios reported online with live
statistics. These readings do not independently prove the video traffic path.

The normal collector avoids disruptive frequency scans. The package also
contains backend/routers/radio_diagnostics.py, but this optional diagnostics
route is incomplete: it imports ingestion.mikrotik_collector while the
included collector is under services/, and backend/main.py does not register
the router. Review its imports and wiring before using it. The regular radio
statistics panel uses the separate working collector and telemetry route.

3. VIDEO STREAMING

The current local bench path is:

  USB webcam -> Chrome H.264 publisher -> MediaMTX -> WebRTC -> phone

Chrome publishes locally over WebRTC. The phone reads the same MediaMTX
stream through the MikroTik network using a second WebRTC connection. The
previous test used two MediaMTX instances linked by RTSP/TCP; the tested
single-server profile removes that relay.

Front Camera embeds the MediaMTX player. The URL comes from
VITE_ROVERCAM_PLAYER_URL when set, otherwise it uses the dashboard hostname,
port 8889 and /rovercam/. Other cameras retain their existing image source
behavior. The player permits autoplay. The simulated FPS, RTT and LIVE
badges are hidden for the WebRTC player.

The low-rate test requested H.264 at 640 x 360, 15 fps and 700 kbps.
Chrome manages its keyframe interval. Short local tests showed advancing
frames at 640 x 360, and the phone user confirmed fresh video with the
single-server setup. A short server-side phone sample showed zero discarded
frames. These checks do not establish long-duration reliability or latency.

MediaMTX uses TCP 8889 for HTTP signaling, UDP or TCP 8189 for WebRTC media,
and loopback-only TCP 9997 for its API. The phone test allowed reading from
192.168.88.252 and local publishing from loopback. The laptop CPE-facing
address was 192.168.88.254. Adapt addresses for the receiving network.

4. TEST FINDINGS AND LIMITATIONS

- The earlier two-server test recorded RTP packet loss, discarded frames
  and an RTSP source timeout. Their origin was not fully isolated.
- A forced local reader disconnect in the single-server setup took about
  19.5 seconds to show a fresh frame. This was one local test.
- An experimental fast-recovery player failed playback verification and
  was not installed in the active dashboard.
- Physical link interruption, non-line-of-sight recovery, end-to-end latency
  and sustained video stability still need measurement.
- Phone playback worked, but simultaneous radio counters and routes were not
  recorded to independently prove each hop in the video path.
- Windows Smart App Control blocked the installed GStreamer tools and
  dependencies of the available FFmpeg build. Security was not disabled.
- The launcher later selected Lenovo FHD Webcam by default. Successful
  capture from that specific camera was not established in the available
  test log. Earlier verified capture used the prior USB Camera.
- The production build and targeted camera checks passed in the earlier
  integration. Project-wide ESLint reported 107 errors and one warning in
  other files at that time.
